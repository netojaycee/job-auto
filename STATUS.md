- 2026-09-22: Drizzle chosen over Prisma for the DB layer (lighter runtime, more SQL control for dedup/queue logic).
- 2026-09-22: VPS sizing plan set — see ARCHITECTURE.md §10. Start at 4vCPU/8GB, scale to 8vCPU/16GB, split services beyond ~300 users.
- 2026-09-22: Monorepo scaffolded (pnpm workspace, Next.js web, NestJS worker, db/ai/types packages). AI provider abstraction implemented (`packages/ai`) supporting Anthropic and any OpenAI-compatible endpoint (Ollama) via `AI_PROVIDER`/`AI_MODEL`/`AI_BASE_URL` env vars — no code changes needed to switch. Full Drizzle schema for the data model in ARCHITECTURE.md §3 written in `packages/db/src/schema.ts`, not yet migrated to a running database.
- 2026-09-22: No Docker locally — local dev uses Postgres/Redis via DBngin directly. Docker is deploy-only. Deployment model set: the server never receives source code, only `deploy/docker-compose.yml` + `deploy/Caddyfile` + a Doppler/manual-SSH-provisioned `.env`. CI (`.github/workflows/deploy.yml`) builds `apps/web`/`apps/worker` into images, pushes to GHCR, rsyncs only the two config files to the server, then triggers a remote `docker compose pull && up -d`. See ARCHITECTURE.md §11.
- 2026-09-22: Auth uses Better Auth mapped onto our own `users` table (extended with `emailVerified`/`name`/`image`/`updatedAt`) rather than letting it own a separate table — keeps `role`/`clusterId` colocated with the rest of the user record. `passwordHash` was dropped from `users`; Better Auth stores credentials in its own `account` table instead.
- 2026-09-22: No paid AI subscription available yet — using Groq's free tier (OpenAI-compatible endpoint) as the working provider during development instead of Anthropic. Zero code changes needed since `packages/ai` already abstracts this; switch to `AI_PROVIDER=anthropic` whenever real budget exists. Added `packages/storage` (R2/S3-compatible client) following the same shared-package convention as `db`/`ai`/`types`.
- 2026-09-22: **Gotcha, resolved:** the Nest CLI's default scaffold uses ESM (`nodenext` module resolution), which requires `.js` extensions on relative imports. Adding those extensions to shared package source (`packages/db`, `packages/ai`) to satisfy the worker's build then broke `apps/web`'s Turbopack build, which consumes those same `.ts` files directly and couldn't resolve the `.js`-suffixed specifiers. Fixed by switching `apps/worker` to CommonJS (`module: "commonjs"`, dropped `"type": "module"`, dropped all the added `.js` extensions) instead — see CLAUDE.md for the details and the `dotenv/config` side-effect-import caveat that comes with it. Also: when adding `drizzle-orm` as a *direct* dependency to a new package/app, pin it to the exact version already used by `packages/db` (currently `0.44.7`) — a bare `pnpm add drizzle-orm` grabs latest and two different drizzle-orm versions in the dependency tree produce confusing "SQL<unknown> is not assignable to SQL<unknown>" type errors since each version's internal types are structurally distinct. Same pinning rule turned out to apply to `ioredis` (BullMQ needs exactly `5.11.1`, not latest `6.x`) — general lesson: always check what version a workspace package already depends on transitively before adding the same package directly elsewhere.
- 2026-09-22: **Critical finding, fixed:** the first version of CV tailoring fabricated an entire fake "Projects" section with invented metrics despite explicit "never invent" instructions in the prompt — see the CV tailoring entry in Phase 2 above. Lesson generalized: for any AI output that could cause real-world harm if wrong (CV fraud, here), verify with an independent second pass rather than trusting a single generation prompt, especially on free-tier/weaker models. Same pattern could apply to cover letters later if similar issues surface.
- 2026-09-22: Wallet logic (`getOrCreateWallet`/`getEffectiveWallet`/`grantCredits`) moved from `apps/web/src/lib/wallet.ts` into a new shared `packages/wallet`, plus a new `debitCredits`/`hasSufficientBalance` pair — the worker's agent orchestration needed the same logic apps/web already had, and CLAUDE.md's own convention says shared logic goes in a package, not duplicated. Same reasoning produced `packages/queue` (BullMQ queue/worker helpers) so both `apps/web` (enqueues from the admin "run now" button) and `apps/worker` (the actual scheduler daemon) share one implementation.
- 2026-09-22: **Safety gate added:** `AGENT_ALLOW_REAL_APPLY` (unset by default) gates the apply step in `runAgentForUser` — everything through CV/cover-letter tailoring runs automatically and has no external side effects (AI calls + our own DB/storage), but actually emailing or portal-submitting to a real employer does. This wasn't in the original architecture and was added deliberately during this session: the Gmail-send and Playwright-portal-apply code was built and typechecked but **never executed against a real recipient/posting** — doing so during development would mean sending fabricated test applications to real companies. Do not flip this to `true` and wire real channel dispatch without a deliberate decision to do so; see ARCHITECTURE.md §12.
- 2026-09-22: Hit Groq's free-tier daily token cap (200,000 tokens/day) partway through a live test, from the cumulative volume of scoring/tailoring calls made across this session's testing. Not a bug — a real, expected constraint of the free tier, and useful validation that a genuinely daily-driving agent (even for one user) can exhaust a free quota within a single day of active development/testing. Reinforces ARCHITECTURE.md §9's point about revisiting the model choice deliberately before going live rather than assuming the free tier scales.
- 2026-09-22: pnpm 11.15.1 has a build-approval mechanism that doesn't fully work via `onlyBuiltDependencies`/`ignoredBuiltDependencies` alone for every package (`msgpackr-extract`, an optional native accelerator pulled in by BullMQ's `msgpackr` dependency, kept re-triggering `ERR_PNPM_IGNORED_BUILDS` and failing `pnpm install`/`pnpm run build` with exit code 1 despite being listed). Fixed by adding an explicit `allowBuilds: { msgpackr-extract: false }` block to `pnpm-workspace.yaml` — this is the mechanism that actually suppresses it. If a similar ignored-build error resurfaces for a different package, try `allowBuilds` before assuming `onlyBuiltDependencies` should have been enough.
